# 行动模式：营切换与战况简报（0.1.2）

房间列表中的原“突破 / Breakthrough”改为“行动 / Operations”。配置路径、玩法 ID 仍沿用 `breakthrough`，旧地图的区域、据点和部署位置可以继续使用。

## 配置镜头

与现有部署镜头和结算镜头的选择方式相同：管理员先站到希望作为简报镜头的位置，调整好朝向和俯仰角，再执行：

```text
/gdc room <房间ID> config breakthrough btBriefingViewPosition here
```

`here` 同时记录 X/Y/Z、yaw、pitch；也支持现有的 `x,y,z,yaw,pitch` 格式。坐标与其他镜头配置一致，X/Z 使用所在方块中心，Y 保留小数。建议选能俯瞰所有区域及双方大本营的高处，并朝地图中心看；镜头前方应能覆盖各区域完整边界。

另外三个参数：

```text
/gdc room <房间ID> config breakthrough btBattalionCount 3
/gdc room <房间ID> config breakthrough btBriefingSeconds 20
/gdc room <房间ID> config breakthrough btPreparationSeconds 10
/gdc room <房间ID> saveRoom
```

这些字段也接入原房间配置界面：简报镜头在“传送”分类，营数和时长在“规则”分类。

| 参数 | 默认值 | 范围 | 含义 |
| --- | --- | --- | --- |
| `btBattalionCount` | 3 | 1–10 | 进攻方总营数 |
| `btBriefingSeconds` | 20 秒 | 8–600 秒 | 到达简报镜头之后的演示时长，不包含往返飞行、退场淡出和攻势提示 |
| `btPreparationSeconds` | 10 秒 | 1–300 秒 | 返回部署位置后才开始的准备时间 |

旧 JSON 缺少营配置时自动使用默认值。多营房间启动前需要补设 `btBriefingViewPosition`；单营房间若未设置则使用当前区域部署镜头作为后备简报镜头。运行中的对局使用开局读取的营参数，新参数在下一场生效。

## 演示流程

本营兵力耗尽或当前区域进攻超时后，服务器暂停占领、伤害和部署推进，并统一清理存活、倒地、死亡、部署中的玩家状态。清理本身不计入死亡或比分。

1. 立即锁定移动、开火、物品使用等战场操作，保留鼠标与聊天，在原镜头停留 **3 秒**。防守方显示“我们赢了 / 成功防守本区域”，进攻方显示“我们输了 / 无法拿下本区域”。文字参考截图采用白色、加大字距、无描边的居中两行，上方大标题、下方小副标题；位置和大小按屏幕比例计算。
2. 用 **7 秒**平滑飞到简报位置，同时转到配置的角度。结果文字持续显示，直到飞行最后 **1 秒**才淡出，到达时完全隐藏。
3. 到位后才开始 `btBriefingSeconds`。先用 **1 秒**淡入所有区域及双方大本营的边界与遮罩。大本营颜色始终按所属阵营显示：己方蓝色、敌方红色。
4. 各区域的起始遮罩统一表示防守方所有，然后按区域顺序，每区用 **0.5 秒**改变到进攻方所有；只改变已经完整拿下的区域。己方蓝色、敌方红色。攻到第三区时，进攻方先看到各区域全红，再依次将第一、第二区变蓝；第三区仍为红色。防守方看到相反配色。
5. 简报时长结束后，用 **1 秒**淡出全部边界、遮罩和简报标题。颜色保持最终战况，不回放变色动画。
6. 遮罩消失后，在画面中央偏上显示 **5 秒**“还有X波攻势”（剩余营数大于一）或“最后攻势”（只剩一营）。文字采用截图中的白色疏排样式，带短暂淡入淡出；期间镜头保持简报位置，战场操作仍然锁定，鼠标与聊天可以使用。
7. 提示结束后用 **2 秒**平滑返回当前区域的部署镜头。
8. 到位后清除简报画面，恢复原部署图标、边界、鼠标和配装入口，并开始准备倒计时。准备结束后使用原部署流程。

调长简报总时长只会延长最终战况画面的停留，不会减慢区域动画。六个区域的淡入和逐区变化共需 4 秒（淡入 1 秒、逐区变色共 3 秒）；简报时长仍保留原 8 秒下限。

换营保留已经完整占领的区域，当前未突破区域的据点归属与进度恢复到防守方，并按重新计算的上限补满新营兵力。区域时间配置 `btStageDurationMinutes` 可设为 `0` 关闭超时；零兵力争夺期间不受区域超时限制。

进攻方拿下全部区域，或最后一营耗尽时，仍先显示结果和简报，将遮罩淡出后进入原整场结算，不显示下一波攻势提示，也不返回新营部署。拿下全部区域的结果文案相应改为攻方“成功拿下全部区域”、守方“无法守住本区域”。

## 兵力规则（0.1.2）

规则分类中的兵力参数：

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `btTroopsPerPlayer` | 20 | 每位参考阵营玩家提供的兵力，支持正数小数 |
| `btTroopBalanceReference` | 根据防守方计算 | 也可选择根据进攻方计算 |
| `btMaxAttackTroops` | 250 | 人数计算结果允许的最大上限，须为正整数 |
| `btStageTroopReward` | 50 | 每次完整攻占区域发放的固定补兵，允许设为 0 |
| `btTroopGainPerDefenderKill` | 3 | 清理撤退守军时，每次符合条件的击杀补兵 |

```text
/gdc room <房间ID> config breakthrough btTroopsPerPlayer 20
/gdc room <房间ID> config breakthrough btTroopBalanceReference 根据防守方计算
/gdc room <房间ID> config breakthrough btMaxAttackTroops 250
/gdc room <房间ID> config breakthrough btStageTroopReward 50
/gdc room <房间ID> config breakthrough btTroopGainPerDefenderKill 3
/gdc room <房间ID> saveRoom
```

上限 = `min(最大兵力上限, 向上取整(参考阵营人数 × 每人提供兵力数))`。人数沿用原规则，统计房间内属于参考阵营的参战玩家，包括倒地、死亡和部署中的成员；观战人员不计入参考阵营。开局、新营准备开始时计算上限并补满。区域攻占成功时按当时人数计算下一阶段上限，实际进入下一阶段时不再计算，也不再次补兵。阶段作战中加入或退出不会立即改变本阶段的上限，在下次区域攻占或新营开始时生效。

区域攻占成功后的固定顺序：

1. 更新上限。上限增加不自动补兵；上限降低也不裁掉已有的超额兵力。
2. 当前兵力不足 50 时，先补至 `min(50, 新上限)`；如果当前兵力已经超出新上限，则原样保留。
3. 发放 `btStageTroopReward`，仅补充新上限以内的空缺。
4. 后续清理撤退守军期间逐次发放击杀奖励，同样不会溢出上限或裁掉原有超额兵力。

例如新上限为 200、攻占时剩 20，则先补至 50，再增加默认 50，得到 100；之后击杀五名撤退守军增加 15，得到 115。若新上限为 70，同样剩 20，则最终只能补至 70。若已有 160、上限降到 100，则仍保留 160，后续自然消耗至低于上限后才允许补兵。区域奖励仅发放一次，进入撤退、推进倒计时和下一阶段不会重复领取。

进攻方倒地不扣兵力，成功救援不扣兵力，确认死亡在正常作战阶段扣 1。防守方普通死亡不减少进攻方兵力。撤退和推进倒计时期间进攻方死亡不扣兵力；只有撤退期间、旧区域边界内、由进攻方击杀的防守方玩家提供奖励。换营清理、传送和重生不扣兵力。

旧房间 JSON 的 `maxAttackTroopsAt12Players` 读取时自动除以 12，转换为 `troopsPerPlayer`；已有的明确计算基准和击杀奖励保留，缺少的新字段使用默认值。保存后只写新字段，不会反复除以 12。原 `btMaxAttackTroopsAt12Players` 配置入口移除，改用 `btTroopsPerPlayer`；不要直接把旧数值填入新配置。

## 零兵力争夺

原“背水一战”和“破釜沉舟”合并为“零兵力争夺”，沿用 `BT_DESPERATE` 音乐及原重生等待设置，HUD 显示实际兵力 **0**，时间显示 `--:--`。不再使用原三分钟/一分钟计时，也不受旧 `enableBackAgainstWall` 开关影响。

兵力归零时，先更新本阶段全部据点状态：已由进攻方完全占领的点允许保留；其余每个点必须仍有部分占领进度，或双方玩家同时处于该点的占领范围内进行争夺。防守方拥有满控制进度、且没有双方同时争夺的任意一个点，会结束本营。双方人数相同时仍算争夺，进度暂时停住不会退出；空点保留部分进度时仍算拉扯。只检查当前阶段的有效据点，不检查后续区域。

进入后可以继续战斗和部署，直到进攻方完全占领本阶段全部据点，或防守方完全控制任意一个点。占领成功走正常补兵和区域推进流程；失败走原营结算、战况简报及下一营准备流程，最后一个营失败才结束整场行动。最后一次死亡、攻占与超时同一服务器 tick 发生时，攻占成功优先，避免误判本营失败。

零兵力 HUD 可用 `/gdc debug preview hud breakthrough zerotroopcontest` 预览；原 `backtowall`、`burnboats` 调试入口也显示新状态。管理员 `exhaustBattalion` 仍直接结束本营以测试简报，不用于验证零兵力争夺。

## 快速实机验证

在有双方玩家的测试房间开局后，可由管理员执行下列命令直接耗尽本营，避免反复制造死亡：

```text
/gdc room <房间ID> exhaustBattalion
```

命令需 OP 2 权限，仅在行动模式的作战阶段可用；会实际消耗当前营，请在测试对局使用。

建议依次确认：

- 同时包含存活、倒地和部署中的玩家，营结束后全部停止移动、攻击、战场交互及配装；管理员也应被锁定。鼠标、聊天输入及聊天记录滚动仍可使用，镜头飞行不受鼠标影响；跨演示阶段不应关闭已打开的聊天框。
- 双方分别看到正确结果文字，等待 3 秒后开始 7 秒飞行，镜头保留配置的朝向与俯仰。
- 攻到第三区再耗尽本营，确认只按顺序改变第一、第二区，双方红蓝相反，双方大本营从淡入开始就是对应阵营颜色，并且不随区域变色。
- 将简报设为 8 秒、45 秒比较，区域动画速度一致；准备倒计时都从返回到位开始。
- 简报时长结束后先退场 1 秒，再显示 5 秒攻势提示，然后开始返程；三营配置第一营后显示“还有2波攻势”，第二营后显示“最后攻势”，第三营后直接结算。
- 返回后可以使用原部署界面、选出生点和调整配装；准备期不能提前出生。
- 在结果、飞行、简报、遮罩淡出、攻势提示和准备阶段分别重连/中途加入，确认跟随当前阶段并使用剩余时间。
- 第三营耗尽和攻占最后区域分别触发整场结算；结算开始即恢复鼠标与聊天，可点击退出房间，仍不能移动、开火或使用道具；管理员中断对局/退出房间后锁定能解除。
- 每个区域真正进入作战时播放一次 `music.stage_begin`；换营后在准备结束、再次开战时也播放。同阶段的持续 HUD 刷新和部署切换不应重复播放。
- 将弹药箱与医疗箱装备的自动补全秒数设为正数并部署，投掷后无需靠近地面弹药箱，等待设定秒数即可恢复一件；达到配置数量后不再补全。设为 0 或禁用自动补全则不恢复。

兵力专项实测还需确认：阶段间增减参考阵营人数，检查上限更新和超额保留；分别用剩余 0/20/50/80 兵力攻占区域，核对保底、固定奖励及撤退奖励顺序；全部剩余点拉扯时耗尽兵力，保持争夺超过原阶段时间，再分别测试攻下全部据点和守方恢复任意一个据点的出口。

自动检查覆盖兵力比例换算、上限增减、补兵顺序、零兵力争夺及同 tick 结算优先级，以及实际生产时间线、遮罩进度、配置保存、区域重置、网络编解码，以及结算锁定优先级、光标与视角输入区分、箱子补全计时和阶段音乐去重；通过本地 Gradle 初始化脚本运行，不随仓库发布。镜头视觉、部署交互和多人同步仍需上述实机验收。

客户端与服务端均须更新到 `0.1.2`，严格网络协议为 `bf1-0.1.2`。

弹药箱、医疗箱的背包数量恢复沿用装备编辑中的 `replenish_seconds`（自动补全秒数），以部署配装中的数量为上限，不改变地面箱子的容量或补给规则。补给包继续按原机制每 6 秒恢复一件、上限两件，其它消耗品仍通过地面弹药箱补给。
